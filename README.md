# ReviewPulse

> AI-powered e-commerce product review intelligence platform.

ReviewPulse helps e-commerce sellers, small teams, and product-focused users understand large volumes of customer reviews and turn them into actionable product intelligence.

Instead of requiring users to manually read thousands of reviews, ReviewPulse processes review datasets and identifies:

- Review health and rating trends
- Positive and negative topics
- Emerging complaint patterns
- Customer sentiment signals
- Potential product promise gaps
- Rating/text contradictions
- Evidence-backed AI findings
- Recommended areas for investigation

---

## 1. Project Vision

ReviewPulse is designed around one core idea:

> **Turn customer reviews into understandable, evidence-backed product intelligence.**

The product should not simply generate AI summaries. It should help users move from:

```text
Raw Reviews
    ↓
Structured Data
    ↓
Analysis
    ↓
Emerging Signals
    ↓
AI Findings
    ↓
Supporting Evidence
    ↓
Business Action
```

Every important finding is linked to real review evidence — reviewers, quotes, time windows, and sample sizes — so users can trust and act on what they see.

---

## 2. Key Features

### 🚨 Early-Warning Radar
Detects emerging complaint patterns before they snowball. Aggregates complaint topics across defined time windows, compares current rates against a documented baseline, and surfaces severity indicators with supporting review evidence.

### 🔍 Promise vs. Reality
Compares stated product claims against actual customer review evidence. Highlights where a product is living up to its promises and where customers report contradictions — backed by review counts and quoted excerpts.

### 🤖 Evidence-First AI Investigator
Uses an LLM (where justified) to produce structured, grounded findings. Every AI-generated insight is validated against real review IDs. No fabricated citations, no hallucinated evidence.

### ⚡ Rating–Reality Contradiction Detector
Flags reviews where the star rating and written sentiment diverge. Helps identify reviews that require closer attention, presented with the original review text and the mismatch reason.

## 4. Architecture Overview

ReviewPulse uses a **modular monolith** — one FastAPI backend with clearly separated feature modules, a PostgreSQL database, a Celery worker for background processing, and a separately deployed Next.js frontend.

```text
Users
  |
  v
Next.js Frontend (Vercel)
  |
  | HTTPS / JSON REST API
  v
FastAPI Application
  |
  +-- Authentication & Workspace Access
  +-- Product & Review Management
  +-- Upload & Ingestion
  +-- Analysis Orchestration
  +-- Evidence & Findings
  +-- Reporting & Exports
  +-- Audit & Health
  |
  +--------------------+
  |                    |
  v                    v
PostgreSQL          Task Queue (Redis)
                        |
                        v
                    Background Worker
                        |
                        +-- Data Validation
                        +-- NLP / Statistical Analysis
                        +-- Complaint Detection
                        +-- Promise vs. Reality
                        +-- Rating/Text Contradiction
                        +-- Optional LLM Calls

Uploaded Files -> Private Object Storage
```

### API conventions

- All endpoints versioned under `/api/v1`
- JSON request/response bodies (except file uploads)
- UTC timestamps in ISO 8601 format
- Consistent error format with machine-readable codes
- OpenAPI docs auto-generated by FastAPI at `/docs`

## 6. Getting Started

### Prerequisites

- **Node.js** >= 18
- **Python** >= 3.11
- **PostgreSQL** (local or managed)
- **Redis** (local or managed)
- An **OAuth 2.0 / OIDC** identity provider (e.g. Google, GitHub)
- An **object storage** bucket (e.g. AWS S3, Cloudflare R2)
- An **LLM API key** (e.g. OpenAI, Anthropic — optional for analysis)

### 1. Clone

```bash
git clone https://github.com/<your-org>/reviewpulse.git
cd reviewpulse
```

### 2. Environment variables

```bash
cp .env.example .env
# Fill in values for your local setup
```

```text
APP_ENV=development
FRONTEND_ORIGIN=http://localhost:3000
API_BASE_URL=http://localhost:8000
DATABASE_URL=postgresql://user:password@localhost:5432/reviewpulse
REDIS_URL=redis://localhost:6379/0
AUTH_ISSUER_URL=
AUTH_CLIENT_ID=
AUTH_CLIENT_SECRET=
OBJECT_STORAGE_ENDPOINT=
OBJECT_STORAGE_BUCKET=
OBJECT_STORAGE_ACCESS_KEY=
OBJECT_STORAGE_SECRET_KEY=
LLM_PROVIDER=
LLM_API_KEY=
LOG_LEVEL=INFO
```

### 3. Backend

```bash
cd backend
pip install -e ".[dev]"
alembic upgrade head
uvicorn app.main:app --reload --port 8000

# Separate terminal — start the worker
celery -A app.workers.celery_app worker --loglevel=info
```

### 4. Frontend

```bash
cd frontend
npm install
npm run dev
# http://localhost:3000
```

## 8. Data Flow

```text
Upload CSV / XLSX
    ↓
Backend: validate file type, size, workspace auth
    ↓
Store file in private object storage
    ↓
Queue ingestion job
    ↓
Worker: parse → validate → normalize → deduplicate → persist reviews
    ↓
Queue analysis job
    ↓
Worker: NLP → Sentiment → Topics → Complaint Detection → LLM (optional)
    ↓
Persist findings + evidence links
    ↓
Frontend fetches via REST API
```

The frontend polls `GET /api/v1/jobs/{job_id}` — it never assumes an upload is done just because the file transfer completed.

## 9. Analysis Pipeline

| Stage | Approach |
|---|---|
| Input validation | Required-field schema checks |
| Normalization | Dates, ratings, whitespace, source metadata |
| Language detection | NLP with confidence score |
| Text quality | Readability measures |
| Topic / aspect analysis | NLP or statistical extraction |
| Sentiment & polarity | Documented NLP method |
| Complaint trend detection | Time-window comparison with sample-size guards |
| Promise vs. reality | Claim-to-review semantic matching |
| Rating–text contradiction | Sentiment vs. star-rating comparison |
| Reliability indicators | Heuristic flags (not fraud determinations) |
| LLM synthesis *(optional)* | Structured output with validated evidence references |
| Persistence | Findings, metrics, evidence links, algorithm provenance |

## 11. Security

- HTTPS enforced in all deployed environments
- Server-side auth and authorization on every protected route
- Workspace-level data isolation — no cross-workspace data leakage
- Upload size limits and file-type validation; files stored privately
- Parameterized DB access via SQLAlchemy — no raw SQL string interpolation
- Secrets via environment variables only — never committed to the repo
- Audit log: auth events, workspace changes, uploads, exports, admin actions
- LLM: minimum required text sent, no credentials in prompts, outputs validated before persistence

## 13. Contributing

1. Branch off `main` with a descriptive name (`feat/complaint-radar`, `fix/ingestion-dupe`).
2. Read the docs before building — `SYSTEM_ARCHITECTURE.md`, `DESIGN_SYSTEM.md`, `COMPONENT_SPECIFICATIONS.md`.
3. Follow the backend module convention: `router.py` → `schemas.py` → `service.py` → `repository.py`.
4. No secrets in commits — `.env` locally, env vars in deployment.
5. Write tests — pytest for backend, framework test utils for frontend.
6. Open a PR with context: what changed, why, and how to test it.
7. Coordinate any schema, API, or auth changes with the full team before merging.
